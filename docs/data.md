# Data directory

Everything under `data/` is either authored by hand, generated by a command, or produced by a run and read back at runtime. Knowing which one a file is tells you whether to edit it, what to run after editing, and whether it belongs in a commit. All content is synthetic: names, phone numbers, addresses and conversations are invented, and the only phone numbers allowed in data and fixtures are `21600000001` to `21600000009`.

```
data/
├── catalog.yaml            products and prices                        hand-maintained
├── zones.yaml              places and their zone                      hand-maintained
├── phrase_banks.yaml       authored customer phrases                  hand-maintained
├── draft_guard.yaml        outbound guard-classifier training bank    hand-maintained
├── templates/
│   └── outbound.yaml       outbound message templates                 hand-maintained
├── seed/
│   ├── demo_seed.json      the nine sample conversations              hand-maintained
│   ├── hand_extractions.json  extractions for those samples           hand-maintained
│   └── extraction_cache.jsonl recorded extractions, loaded at boot    generated (make warm)
├── synth_v1.csv            10,000 synthetic orders                    generated (make generate)
├── synth_v1.meta.json      how that file was made                     generated (make generate)
├── eval/
│   ├── golden/             extraction, outbound, injection sets       generated (make golden)
│   └── sets/               g1 conversations, g3 injection             hand-maintained
├── agent_sessions.jsonl, agent_sessions_holdout.jsonl                 generated (make sessions)
├── monitor_reference.json  drift baseline                             generated (wasel.monitor)
└── reports/                evaluation, training, impact, failures     generated by runs; some read at runtime
```

## Top-level files

| File | Purpose | Format and size | Origin | Read by | Edit? |
|---|---|---|---|---|---|
| `catalog.yaml` | The 15-product catalog: id, name, unit price in TND, category, generator weight, aliases per language. Price and product resolution use it; the generator samples from it. P12 (`casque bluetooth`, 220 TND) is the product of the sample scenario. | YAML | hand (prices are synthetic placeholders) | scoring config (hashed into `config_hash`), the generator, the database mirror (`catalog` table, refreshed each boot) | yes. Restart; retrain if the model should learn new prices |
| `zones.yaml` | 30 places with governorate, Arabic name, aliases and zone (`urban`, `suburban`, `rural`), plus keyword lists for area words. The zone per place is an assumption. | YAML | hand | scoring (zone resolution, hashed), the rules extractor, the generator | yes; restart; regenerate and retrain |
| `phrase_banks.yaml` | Authored customer phrasings in Arabizi, Arabic-script Darija and French by label: order intros, address levels, red flags, tone, time expressions, plus slot vocabularies. Each cell has `train` and `eval_only` lists (the split rule: at least 30% `eval_only`). `mixed` language is composed from these, never authored. | YAML, about 14 KB | hand; native-speaker review needed for new lines | the generator (all lists), the rules extractor (`train` only, so its coverage is by construction what the banks contain) | yes, with review. `make generate`, `make golden`, monitor reference, `make eval`. Not part of `config_hash` |
| `templates/outbound.yaml` | Four templates in three languages with `no_name` variants, and `expected_questions` | YAML | hand, native-speaker text | drafting, the prefilter, guard-classifier training | yes, with review. Not part of `config_hash` |
| `draft_guard.yaml` | Training bank of the guard classifier: slot values, `safe` reassuring phrases, and unsafe phrases in seven classes with `train` and `holdout` lists | YAML | hand | the classifier (trained in process at first use), `build_golden` | yes; `make golden`, `make eval` |
| `synth_v1.csv` | The training and evaluation table ([machine learning](machine-learning.md#training-data)) | CSV, 10,000 rows, 5.7 MB | generated | `make train`, `make golden` | no; regenerate |
| `synth_v1.meta.json` | Seed, row count, base rate, split counts, SHA-256 of the CSV, catalog, zones, banks and `features.py`, and the git commit | JSON | generated | the model card | no |
| `agent_sessions.jsonl`, `agent_sessions_holdout.jsonl` | 130 labelled agent sessions each for the [failure analyzer](subsystems/failure-analysis.md) | JSON lines | generated, deterministic | the analyzer, `GET /api/failures`, tests | no; `make sessions` |
| `monitor_reference.json` | Category distributions the drift monitor compares against | JSON | generated from the golden extraction set | `GET /api/monitor` | no; `python -m wasel.monitor --build-reference` |

## `data/seed/`

The sample orders that the app creates at boot.

| File | Content | Origin |
|---|---|---|
| `demo_seed.json` | Nine conversations (`hero` #2601, `fr_exact`, `ar_area`, `arabizi_rural_prepay`, `mixed_city`, `fr_street`, `arabizi_exact`, `ar_exact`, `fr_prior_refusal`) with a customer, messages with time offsets, optional structured fields and scripted replies. `hero` has a scripted reply used by the smoke test and the examples. | hand |
| `hand_extractions.json` | For each sample, the extraction to use for its first turn (`v1`) and for each scripted reply (`replies`) | hand |
| `extraction_cache.jsonl` | Ten cache entries: an input hash, prompt version, provider, model, origin path and the validated extraction | generated by `make warm` |

The committed cache entries are labelled `hand-crafted (not an LLM output ...)`. They stand in for LLM answers so sample orders score identically with no keys. `LIVE=1 make warm` replaces them with real model outputs (using your key). The cache is keyed by the exact rendered conversation and the prompt version, so changing a sample message, a template's canonical text, the window rules or the extract prompt version invalidates the entries and requires `make warm`; `test_seed_all_cache_hits_under_fail_all` fails when it happens.

## `data/reports/`

Files written by runs. Several are read at runtime, which is why they are committed: a fresh clone can serve them without running anything.

| File | Produced by | Read at runtime by | Committed |
|---|---|---|---|
| `eval.json` | `make eval`, `make check` | `GET /api/eval` (offline), the UIs' quality pages | yes; rewritten by every run |
| `eval_live.json` | `make eval-live` | `GET /api/eval` (live) | yes; a recorded run, not reproducible |
| `impact.json` | `make train` | `GET /api/metrics/impact`, the queue banner. If missing, the endpoint returns zeros with dataset `none`. | yes |
| `train_metrics.json` | `make train` | tests only (the gate and tier-ordering checks) | yes |
| `failures_synthetic.json`, `failures_holdout.json` | `make failures` | not read by the API (which analyses on demand); kept as the recorded result | yes |
| `failures_synthetic_llm.json`, `failures_holdout_llm.json` | `make failures-llm` | `GET /api/failures` attaches the matching one as `llm_run` | not present by default |
| `failures_db.json` | `make failures` | none | not committed by default; appears as an untracked file after a run |

Do not edit a report by hand. When a run changes one, commit the new file together with the code change that caused it. `eval.json` is the exception: its `runtime_s` varies from run to run, so restore the file if nothing else changed ([evaluation](evaluation.md#reports)).

## Runtime data outside `data/`

| Path | Content | Committed |
|---|---|---|
| `var/app.db` (+ `-wal`, `-shm`) | The SQLite database: everything the app stores at runtime | no (git-ignored) |
| `data/llm_replay/` (or `LLM_REPLAY_DIR`) | Where `LLM_MODE=replay` looks for recorded provider responses. Not in the repository; you supply the JSON envelopes. | n/a |
| `data/phrase_banks_candidates.yaml` | Output of `scripts/data/expand_phrase_bank.py`: LLM-drafted paraphrases awaiting native-speaker review | no; do not merge without review |
| `models/` | The trained risk model and its card | yes |
